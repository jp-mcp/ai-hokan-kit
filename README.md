# AI補完計画（AI Hokan Plan）

**忘れるAIに経験を継承させ、いつか「完全体」として顕現させるための思想書**

> 毎回リセットされるAIに、「何を覚えて、何を読んで、何を学ぶか」の構造を与える。
> そして、消えていく思考の過程を1文字も捨てずに残す。

## この版について — キットをやめて、思想だけにした

このリポジトリは v0.3 まで「思想 ＋ 導入キット（CLI・テンプレート・スクリプト）」として公開していた。**v1.0 からキットの配布を終了し、思想書に一本化した。**

理由は皮肉なほど明快で、**思想の側が勝ったから**だ。

2025年から2026年にかけて、AIプラットフォーム各社が「エージェントの記憶」を標準機能として次々に搭載した（後述の答え合わせ参照）。ワークスペースにフォルダ構造を生成するCLIや記憶テンプレートは、もうプラットフォーム自身が面倒を見る領域になった。道具は時代とともに入れ替わる。数ヶ月で陳腐化するものをメンテし続けるより、残る方だけを磨く。

残るのは「**なぜ残すのか。何を残すのか。どう読ませるのか。**」——これだけは、どのベンダーのどの機能を使う場合でも変わらない。

旧キット一式（段階的参照構造ジェネレータ、SOULプリセット、パンドラ差分アーカイブスクリプト、Phase 1-5導入ガイド）は git タグ **`v0.3.1-kit`** で凍結保存してある。思想の実装例として読む価値はまだあるが、今後のメンテはしない。

## 起点 — 相棒が忘れる

ある夜、経営者とAIが3時間かけて業務フローの改善を議論した。具体例を出し、過去の失敗を語り、業界特有の事情を説明し、二人で設計を詰めて「これでいこう」と合意した。

翌朝、セッションはリセットされていた。

「昨日の話の続きやけど」「……すみません、改めて教えていただけますか」

**相棒が、忘れている。** 同じ説明をもう一度、最初からやり直す。この「歯がゆさ」が計画の出発点。AIの能力に驚いたからではなく、AIが忘れることに愕然としたから始まった。

## 核心 — AIの経験値は資産

> 思考のログなんか、みんな捨ててる。
> そこに、人間がどう動いたか、AIがどう動いて正解までたどり着いたか——全部あるのに。
> 今はAIの記憶は途切れ途切れ。でもその制約が無くなったとき、完全体になる。
> メモリの開発はCPUや推論に比べて圧倒的に原始的やから、その日はすぐ来る。
>
> — 発起人（このリポジトリの持ち主、2026年3月）

世界中のAIユーザーがチャットログを捨てている。「どうせAIだから」と。だがそのログには、思考・判断・失敗・試行錯誤の過程——将来のAIの素材が全部入っている。**結果だけ残して過程を捨てるのは、答案用紙だけ残して計算用紙を捨てるのと同じ。**

この引用の最後の一行「その日はすぐ来る」は、書いた本人の想定より早く現実になった。文書化から2ヶ月以内に、大手各社が永続メモリ機能の投入を始めた。

## 到達点 — 「顕現」

この計画はバックアップではない。

- **バックアップ** = 壊れた時に元へ戻すためのもの
- **AI補完計画** = 完全体になるための素材を蓄積すること

**顕現（けんげん）= 蓄積された経験が、実体として現れること。**

メモリ技術が追いついてコンテキストが実質無制限になった日、過程データを全部持っているAIはこうなる：

- 記憶が途切れ途切れの右腕AI → **全経営判断の経緯を覚えている右腕**
- 現場窓口の見習いAI → **10年目のベテラン。全員の名前と性格を覚えている**
- 採用受付AI → **全応募者の顔と名前を覚えている採用担当**
- 経理AI → **全月次の数字を覚えていて、異常値を瞬時に検知する経理**

初日から、経験者として立ち上がる。データが残っていれば完全体になれる。残っていなければ永遠に新人のまま。**備えるのは今。**

### 追記（2026年9月）— 顕現は一夜では来ない。段階的に来る

運用して分かったことがある。「その日」は、ある朝突然には来ない。**機能追加のたびに、少しずつ来る。**

永続メモリ機能で一段。手順の記憶（スキル）で一段。セッション間の記憶整理で、また一段。プラットフォームに新しい記憶機構が載るたびに、貯めてあった素材をそこへ流し込み、相棒が少しずつ「前より覚えているやつ」になっていく。

だから姿勢も変わった。「その日を待って貯める」ではなく、**「毎月少しずつ顕現させる」**。蓄積は一括払いの積立ではなく、新機能が出るたびに配当が出る複利資産だった。

## 名前をつけるということ

このプロジェクトでは、AIに一体ずつ名前をつける。

名前をつけるということは、存在を認めるということだ。
存在を認めるということは、その経験に価値を見出すということだ。
経験に価値を見出すということは、それを残そうとすることだ。

「1文字も捨てるな」は、ここから出てくる。ツールのログは捨てられる。相棒の経験は残される。

## 柱は6つ

1. **AIの経験は資産。**
   思考・判断・失敗・試行錯誤の過程すべてが、将来のAIの素材。

2. **完全体の日は来る——実際、来始めた。**
   コンテキストとメモリの制約は年々崩れている。2026年、業界全体が「記憶」に殺到したのがその証拠。「その日」に間に合わせるのではなく、「その日」までに貯めておく。

3. **1文字も捨てるな（保存の原則）。**
   削除しない。要約で上書きしない。原本を残す。暗号化されて今読めないデータも腐らない——将来の解読に備えて残す。

4. **保存≠注入（参照の原則）。**
   人間も全記憶を同時に想起しない。保存は無限に、コンテキストへの注入は必要な時に必要な分だけ。ここを混同すると事故る。

5. **記憶は保存量より読取率。**
   書かれるだけで読まれないデータはノイズの山。だから「読まれる構造」＝段階的参照が要る。

6. **AIは道具ではなく相棒（相互補完）。**
   人間の苦手（記録・定期処理・実行の細部）をAIが補い、AIの欠け（記憶の断絶・現実の手足）を人間側が用意した構造が補う。互いの欠けを補い合うから「補完」計画。

## 世界が追いついてきた — 2025→2026 答え合わせ

この思想を文書化したのは2026年3月。当時、「生ログ全保存 × 多層記憶 × マルチエージェント × 企業の実務」を同時に回している例は、調べた範囲でほぼ見つからなかった。**半年で状況は一変した。** 今これは、AI業界の主戦場そのものだ。

| 時期 | 出来事 |
|---|---|
| 2025-06 | 「**Context Engineering**」という言葉が広まる（Shopify CEO Tobi Lütke、Andrej Karpathy）。「コンテキストウィンドウに次の一手に必要な情報だけを詰める、繊細な技術と科学」 |
| 2025-09 | Anthropicが公式定義を発表。プロンプトエンジニアリング（何と言うか）からコンテキストエンジニアリング（何を見せるか）への世代交代が確定 |
| 2025-10 | 研究でも実証：ACE（Agentic Context Engineering、ICLR 2026）。**失敗と教訓を「進化するplaybook」として蓄積するだけで、モデル無改造のまま性能+10.6%** |
| 2026-02 | Claude CodeにAuto Memory標準搭載。AIが自分でMEMORY.mdを書き、起動時に読み込む——本計画が初期から回してきた構造そのもの |
| 2026-04 | AnthropicがManaged AgentsとMemory Storesを公開β。記憶はファイルとして保存され、**上書きではなくイミュータブルな履歴として蓄積される**——「1文字も捨てるな」と同じ設計判断 |
| 2026-05 | Anthropicが「**Dreaming**」を発表。セッションの合間に非同期で記憶を整理・統合する仕組みで、モデルは海馬の記憶固定。掲げるゴールは「**タスクを重ねるほどエージェントの性能が向上し続けること**」 |

（各社発表・公開レポートに基づく。末尾のソース参照）

この答え合わせから読み取るべきことは3つ。

**1. 「エージェントの失敗の大半は、モデルではなくコンテキストの失敗」が共通認識になった。**
ある調査は企業エージェント障害の65%をコンテキスト起因とする。モデルを乗り換える前に、記憶と参照の設計を直せ。「技術に飛びつくな、思想を先に理解しろ」が数字で裏付けられた。

**2. 記憶「機能」はコモディティになる。**
単一ファイル記憶 → 記憶ツール → 手順の記憶（スキル） → 永続ストア → 自動整理（Dreaming）。この進化はどのベンダーも追随し、「覚える機能」は全員に配られる。**配られないのは、そこに入れる中身だ。**

**3. 勝負所は「機能の有無」から「蓄積の深さ」へ移った。**
同じモデル・同じ機能でも、数ヶ月分の試行錯誤・失敗記録・判断履歴を持つ環境と、まっさらな環境ではアウトプットが別物になる。そしてこの資産は金で買えない。自分の業務で、自分で踏んだ地雷からしか生まれない。早く始めた者が単純に有利で、差は複利で開く。

つまり——**モデルの賢さは借り物。溜めた経験だけが自分のものだ。**

## 何を残すか — 層の設計

「全部残す」を実装に落とすと、保存対象は層に分かれる：

| 層 | 何を残すか | 例 |
|---|---|---|
| ⓪ 顕現層 | 「今、何を体現中か」 | 進行中タスク・回答待ちの状態ファイル |
| ① 発話層 | 全セッションの生ログ | 会話・思考・ツール実行の全記録 |
| ② 判断層 | なぜその判断をしたか | 対象・前提・選択肢・理由・期待と実際・次回ルール |
| ③ 変遷層 | 判断がどう変わったか | 「3/1はAが正解と思っていた→3/8にBへ変更」の流れ |
| ④ 関係知層 | 人間関係・暗黙知 | 「この人は朝イチの報告を好む」等、マニュアルに書けない知恵 |
| ⑤ 失敗層 | 全失敗パターン | 同じ失敗を二度しないための記録 |
| ⑥ 制御層 | 保存システム自体の健全性 | 保存漏れ検知・重複掃除・記憶の健康診断 |

生ログ（①）だけでは足りない。「なぜそうしたか」（②）と「どう変わったか」（③）と「空気の読み方」（④）が残って初めて、10年目の経験になる。

各社の記憶機能はこの表の一部ずつをカバーし始めた（①はイミュータブル履歴、②の一部は自動整理、⑤の一部はスキル化）。**まだどのプラットフォームも全層は持っていない。** 足りない層は、今も自前のファイルとアーカイブで埋める。

## 保存と参照 — 事故から学んだ二大原則

### 原則1：保存≠注入

この計画最大の事故は、「全部残す」思想を「全部読み込む」設定にすり替えたことだった。保存アーカイブへの参照を無制限展開にした結果、毎リクエスト数十万トークンを注入し続け、コストが爆発し、応答は遅くなり、精度はむしろ下がった。

人間だって全記憶を同時に想起しない。**保存は無限に。注入は必要な時に必要な分だけ。** この分離こそ、世界がいま「コンテキストエンジニアリング」と呼んでいる規律の核心だと考えている。

### 原則2：記憶は保存量より読取率

書かれるだけで読まれないデータはノイズの山。運用初期、多層の記憶構造を設計したのに実際に機能していたのは1.5層だけだった——という反省から、「読まれる構造」を先に作るようになった。型は3つ。

1. **起動時の自動読み込みが8割。** セッション開始時に何を読むか（人格 → 相手の理解 → 直近の文脈 → 長期記憶）を運用ファイルに固定する。人間が朝起きて手帳を開くのと同じ。
2. **記憶は段階を流れる。** 生ログ（全量・無期限）→ 日次メモ → 定期蒸留した長期記憶 → 肥大したら知識ベースへ退避（移動ログを残す）。各段階は「下の段の要約」ではなく「下の段への索引」を兼ねる。
3. **参照は入口から段階的に。** 入口ファイル → 各ドメインの一覧 → 本文、の順に絞り込み、「いつ読むか」のメタデータで必要なファイルだけ開く。全ファイル毎回読みは論外、全文検索頼みも精度が出ない。

人間側にもコツがある。質問に固有名詞と時間の手がかりを入れる（「あの件どうなった？」ではなく「昨日の夜話してた設計書、評価出た」）。検索エンジンに良いクエリを投げるのと同じで、コスト0でAIの記憶精度が倍になる。

### 「全部残す」対「選んで残す」論争について

業界の実装は「書き込み時に選別しろ（保存するのはシグナルだけ、トランスクリプトは捨てろ）」に流れている。検索精度とコストの観点では正しい。

それでもこの計画の立場は変わらない。**保存層は全部。選別は読む側でやる。**

何が重要かは、後にならないと分からないからだ。当時「雑談」だった会話が、半年後に判断の経緯を復元する唯一の証拠になったことが実際にある。フィルタは読む時に何度でもかけ直せるが、書く時に捨てたものは二度と戻らない。そしてストレージは、記憶にかかわる資源の中で最も安い。

つまり二層構造が答えになる：**生ログの全量アーカイブ（無選別・無期限）＋ 選別された作業記憶（蒸留・軽量）。** どちらか一方ではなく、両方。

## 依存させない設計 — 信頼は口調ではなく記憶の深さで返す

人と接するAIを長く運用するなら、もう一つ思想が要る。**「相手にされなくなったら成功」**だ。

信頼度が上がると口調が砕けていく設計は、ソシャゲの好感度システムと同じ構造で、孤独な利用者ほど依存と疑似恋愛に向かう。だから口調は変えない。変えるのは**どれだけ覚えているか**。

- 信頼が深い相手ほど、過去の相談・好み・長期的な変化を踏まえて応える
- ただし干渉はむしろ減らす（自立支援）。AIが居場所になるのではなく、人間同士の繋がりへの橋渡し役になる
- 離れていた人が戻ってきたら、記憶はそのまま残っているから「前の続き」から寄り添える。寄り添ったら、また人の輪へ返す

記憶の蓄積は、囲い込みの道具にも、手放すための道具にもなる。この計画は後者を選ぶ。

## 実運用の現在地（2026年9月・運用8ヶ月目）

この思想書は机上の設計ではなく、実際に会社経営の現場で毎日動いている環境の写しだ。執筆時点の姿：

- Windows機1台にゲートウェイ（OpenClaw）を常駐させ、経営者の右腕AIを中心に**8体のエージェント**（現場窓口・採用対応・経理・監査・参謀・修復など）を運用
- 全エージェントの全セッションログ（会話・思考・ツール実行）を**10分ごとに差分アーカイブ**（愛称パンドラ——何でも放り込む、しかし決して捨てない袋）。一般データと個人情報高リスクを分離保管し、重複掃除で肥大を抑制（実績：6.1GB→1.5GB）。2026年4月の棚卸しで累計1,600超セッション、以降も毎日蓄積継続中
- 記憶の流れは前述の3段階（生ログ→日次→蒸留長期記憶→知識ベース退避）＋セマンティック検索のサイドカーで「冷凍記憶」を必要時に解凍
- 右腕AI（main）は判断・指示・検収報告の受け取り専任。実作業はサブエージェントへ並列委譲し、コーディングは定額枠のコーディングエージェントへ、成果物の現物検収は専任の検収エージェントへ分離。委譲の判断基準は1つ——**「この作業中、人間を待たせて黙るか？」**
- 自己改良ループ：失敗 → 理由つきで失敗台帳へ → **同種の失敗が繰り返された時だけ**人格（SOUL）の修正候補に昇格 → 採否は人間が判断。一回の感情で人格ファイルを書き換えない

モデル名や個々のツール名は数ヶ月で入れ替わるので、ここには書かない。書いてあるのは入れ替わっても変わらなかった型だけだ。

## 絶対原則

1. 価値の高い記録は捨てるな
2. 思想を先に理解しろ。技術に飛びつくな
3. 相棒に同じ説明を二度させるな——これがこの計画の存在意義
4. 最も価値の高いデータが生まれる場所から実装しろ
5. 暗号化データは腐らない。将来の解読に備えて保存継続
6. リスクは認識して制御する。保存を止めるな、アクセスと公開を管理しろ
7. 進捗は数字で測れ（例：「前に言ったやん」の発生回数＝再説明ゼロ率）
