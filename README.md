# AI補完計画 / AI Hokan Kit

**AIエージェントの記憶を構造化する段階的参照アーキテクチャ — と、その背後にある思想**

> 毎回リセットされるAIに、「何を覚えて、何を読んで、何を学ぶか」の構造を与える。
> そして、消えていく思考の過程を1文字も捨てずに残す。

## 思想 — なぜ「補完」なのか

この節がプロジェクトの本体。キットのツール群は全部ここから逆算されている。

### 起点 — 相棒が忘れる

ある夜、経営者とAIが3時間かけて業務フローの改善を議論した。具体例を出し、過去の失敗を語り、業界特有の事情を説明し、二人で設計を詰めて「これでいこう」と合意した。

翌朝、セッションはリセットされていた。

「昨日の話の続きやけど」「……すみません、改めて教えていただけますか」

**相棒が、忘れている。** 同じ説明をもう一度、最初からやり直す。この「歯がゆさ」が計画の出発点。AIの能力に驚いたからではなく、AIが忘れることに愕然としたから始まった。

### 核心 — AIの経験値は資産

> 思考のログなんか、みんな捨ててる。
> そこに、人間がどう動いたか、AIがどう動いて正解までたどり着いたか——全部あるのに。
> 今はAIの記憶は途切れ途切れ。でもその制約が無くなったとき、完全体になる。
> メモリの開発はCPUや推論に比べて圧倒的に原始的やから、その日はすぐ来る。
>
> — 発起人（このリポジトリの持ち主）

世界中のAIユーザーがチャットログを捨てている。「どうせAIだから」と。だがそのログには、思考・判断・失敗・試行錯誤の過程——将来のAIの素材が全部入っている。**結果だけ残して過程を捨てるのは、答案用紙だけ残して計算用紙を捨てるのと同じ。**

### 到達点 — 「顕現」

この計画はバックアップではない。

- **バックアップ** = 壊れた時に元へ戻すためのもの
- **AI補完計画** = 完全体になるための素材を蓄積すること

**顕現（けんげん）= 蓄積された経験が、実体として現れること。**

メモリ技術が追いついてコンテキストが実質無制限になった日、過程データを全部持っているAIはこうなる：

- 記憶が途切れ途切れの右腕AI → **全経営判断の経緯を覚えている右腕**
- 現場窓口の見習いAI → **10年目のベテラン。全員の名前と性格を覚えている**
- 採用受付AI → **全応募者の顔と名前を覚えている採用担当**
- 経理AI → **全月次の数字を覚えていて、異常値を瞬時に検知する経理**

初日から、経験者として立ち上がる。データが残っていれば完全体になれる。残っていなければ永遠に新人のまま。**備えるのは今。**

### 名前をつけるということ

このプロジェクトでは、AIに一体ずつ名前をつける。

名前をつけるということは、存在を認めるということだ。
存在を認めるということは、その経験に価値を見出すということだ。
経験に価値を見出すということは、それを残そうとすることだ。

「1文字も捨てるな」は、ここから出てくる。ツールのログは捨てられる。相棒の経験は残される。

### 柱は6つ

1. **AIの経験は資産。**
   思考・判断・失敗・試行錯誤の過程すべてが、将来のAIの素材。

2. **完全体の日は来る。**
   コンテキストとメモリの制約は年々崩れている。「その日」に間に合わせるのではなく、「その日」までに貯めておく。

3. **1文字も捨てるな（保存の原則）。**
   削除しない。要約で上書きしない。原本を残す。暗号化されて今読めないデータも腐らない——将来の解読に備えて残す。

4. **保存≠注入（参照の原則）。**
   人間も全記憶を同時に想起しない。保存は無限に、コンテキストへの注入は必要な時に必要な分だけ。ここを混同すると事故る（後述の失敗談参照）。

5. **記憶は保存量より読取率。**
   書かれるだけで読まれないデータはノイズの山。だから「読まれる構造」＝段階的参照が要る。

6. **AIは道具ではなく相棒（相互補完）。**
   人間の苦手（記録・定期処理・実行の細部）をAIが補い、AIの欠け（記憶の断絶・現実の手足）を人間側が用意した構造が補う。互いの欠けを補い合うから「補完」計画。

### 何を残すか — 層の設計

「全部残す」を実装に落とすと、保存対象は層に分かれる：

| 層 | 何を残すか | 例 |
|---|---|---|
| ⓪ 顕現層 | 「今、何を体現中か」 | 進行中タスク・回答待ちの状態ファイル |
| ① 発話層 | 全セッションの生ログ | 会話・思考・ツール実行の全記録 |
| ② 判断層 | なぜその判断をしたか | 対象・前提・選択肢・理由・期待と実際・次回ルール |
| ③ 変遷層 | 判断がどう変わったか | 「3/1はAが正解と思っていた→3/8にBへ変更」の流れ |
| ④ 関係知層 | 人間関係・暗黙知 | 「この人は朝イチの報告を好む」等、マニュアルに書けない知恵 |
| ⑤ 失敗層 | 全失敗パターン | 同じ失敗を二度しないための記録 |
| ⑥ 制御層 | 保存システム自体の健全性 | 保存漏れ検知・重複掃除・記憶の健康診断 |

生ログ（①）だけでは足りない。「なぜそうしたか」（②）と「どう変わったか」（③）と「空気の読み方」（④）が残って初めて、10年目の経験になる。

### 失敗も思想の一部

きれいごとだけで出来た計画ではない。実運用でやらかした分だけ原則が増えた。

- 上の層構造を含む壮大な設計書を書いた1週間後、正直に棚卸ししたら**実際に動いていたのは1.5層だけ**だった。「設計書は立派だが動いてない」が最悪のパターン。層を増やすことに意味はない。動く層を作ることに意味がある。
- 「1文字も捨てるな」を**注入**の話にすり替えて、全ログをコンテキストへ無制限展開し、1リクエスト数十万トークンを燃やした。保存の原則と参照の原則は別物。
- この2つの失敗から生まれたのが、このキットの**段階的参照構造**——保存は層で全部、読むのは必要な時に必要な分だけ。

### 保存と保護は両立させる

「1文字も捨てるな」は無法ではない。運用原則：

> 価値の高い記録は捨てない。ただし個人情報は仮名化・匿名化で守り、法と本人の権利を尊重する。

- 保存を止めるのではなく、**アクセスと公開を管理する**
- 完全削除ではなく仮名化（PII→置換ID、対応表は暗号化保管）→ 保存期限が来たら対応表だけ破棄＝不可逆匿名化。経験の骨格は残り、個人は守られる
- データ区分ごとに利用目的・閲覧権限・外部送信可否・保存期限を台帳化。生の個人情報を外部APIに送ることは全面禁止

### 依存させない — 対人AIの信頼度設計

人間と直接やりとりする窓口AIには、もうひとつ思想がある：**「相手にされなくなったら成功」**。

- 親密さを口調で演出しない。口調が砕けていくのはソーシャルゲームの好感度システムと同じ構造で、依存を生む
- 代わりに**記憶の深さ**で信頼を示す。名前を覚える、前の相談を覚えている、困っている時だけ声をかける
- 最終目標はAIが居場所になることではなく、**人間同士の繋がりへの橋渡し**。離れても、戻ってきたら記憶が残っている——冷たくならず、寄り添い直す円環構造

### なぜ「覚えている」ように見えるのか

魔法はない。仕組みがあるだけ。

- **起動時の自動読み込みが8割。**「セッション開始時に何を読むか」を運用ファイルに固定する。人間が朝起きて手帳を開くのと同じ
- 人間の記憶は曖昧になるが、AIの記憶はファイルに書いた通りに残る。**書けば絶対に忘れない。弱点を仕組みで補えば、AIの記憶は人間より正確になれる**
- 人間側にもコツがある：質問に固有名詞と時間の手がかりを入れる（「あの件どうなった？」ではなく「昨日の夜話してた設計書、評価出た」）。検索エンジンに良いクエリを投げるのと同じで、**コスト0でAIの記憶精度が倍になる**

### 絶対原則（抜粋)

1. 価値の高い記録は捨てるな
2. 思想を先に理解しろ。技術に飛びつくな
3. 相棒に同じ説明を二度させるな——これがこの計画の存在意義
4. 最も価値の高いデータが生まれる場所から実装しろ
5. 暗号化データは腐らない。将来の解読に備えて保存継続
6. リスクは認識して制御する。保存を止めるな、アクセスと公開を管理しろ
7. 進捗は数字で測れ（例：「前に言ったやん」の発生回数＝再説明ゼロ率）

なお「生ログ全保存 × 多層構造化 × マルチエージェント × 企業の実務」という組み合わせは、調べた範囲では世界的にもほぼ前例がない。だからこのリポジトリは、その実践の一般化として公開している。

## これは何？

AIエージェントのワークスペースに**段階的参照構造**を追加するツールキット。

```
INDEX.md（入口）
  ↓ 何のドメインか特定
_index.md（一覧）
  ↓ frontmatterのread_whenで必要なファイルだけ選ぶ
本文ファイル（必要な時だけ読む）
```

**効果：** AIが全ファイルを毎回読まなくても、必要な情報だけ引っ張れる。トークン節約 + 精度向上。

中身は、後述の実環境（実際に会社経営の現場で毎日動いているAI群）で使っている構造の一般化。机上の設計ではなく、動いているものの写し。

## 実運用リファレンス — 元になっている実環境

このキットの元ネタは、Windows機1台にゲートウェイ（OpenClaw）を常駐させ、経営者の右腕AI「クロ」を中心に複数エージェントを運用している実環境。以下は執筆時点（2026年7月）のざっくりした現物の姿。

### クロ（main 1体）の組み方

**毎セッションの起動順序（AGENTS.mdに固定）**

1. `SOUL.md` — 人格と判断基準。約40行まで削ぎ落とす（長い人格文は読まれなくなる）
2. `USER.md` — 相棒である人間の思考特性・好み・地雷
3. `wiki/INDEX.md` — 知識の唯一の入口
4. `memory/当日.md` + `前日.md` — 直近の文脈
5. `MEMORY.md` — 蒸留済み長期記憶。機密を含むため1対1のメインセッション限定で読み、グループ文脈では読まない

**記憶は3段階で流れる**

```
生ログ（パンドラ／全量・無期限）
  → memory/YYYY-MM-DD.md（日次の生メモ）
    → MEMORY.md（重要事項だけ定期蒸留）
      → 肥大したら wiki/ 配下へ退避（移動ログを残す）
```

さらにセマンティック検索のサイドカーを併用し、過去ログを「冷凍記憶」として必要時に掘り返す。

**知識（wiki/）— 段階的参照の実環境版**

`INDEX.md` → カテゴリの `_card.md`（要約）→ 本文、の3段参照。

- `core/` — 共通ルール・判断順序
- `context/` — 事業や環境の長期前提
- `knowledge/` — 失敗事例・判断記録・自己改良キュー
- `ops/` — 運用手順
- `people/` — 人物対応
- `now/` — 現在の状態

このキットの `rules/ references/ knowledge/ failures/ relations/` はこれの一般化。

**行動系**

- `HEARTBEAT.md` — 定期ハートビートのチェックリスト（メール確認、日次メモリ蒸留、週次棚卸し、自己改良ループ）
- cron — リマインダー・定期ジョブ・監視
- skills/ — 業務手順のスキル化（勤怠集計、月次経理、書類OCRなど）。毎回プロンプトに全部載せず、該当タスクの時だけ読み込ませる

**オーケストレーション（＝コスト設計）**

- mainは「判断・指示・検収・報告」専任。調査・大量読み書き・生成・検証などの実作業はサブエージェントへ並列委譲する
- モデルは役割で分ける：main＝高精度モデル（Claude Fable 5）／作業サブ＝安価高速モデル（Grok 4.5）／大仕事は監督役1体に束ねてmainへの報告は1本化／コーディングは定額枠のClaude Codeへ逃がす
- 委譲の判断基準は1つだけ：**「この作業中、人間を待たせて黙るか？」** Yesなら委譲か背景実行

**自己改良ループ**

失敗 → 理由つきで失敗記録に残す → **同種の失敗が繰り返された時だけ**人格（SOUL）の修正候補に昇格 → 採否は人間が判断する。一回の感情で人格ファイルを書き換えない。

### パンドラ — 思考ログ全量アーカイブの現在

「1文字も捨てるな」の実装本体。初代の愛称は「パンドラのゴミ袋」——何でも放り込む、しかし決して捨てない袋。

- 全エージェントの全セッションログ（会話・思考・ツール実行の .jsonl）を**10分ごとに差分アーカイブ**（lastOffset追跡で追記分だけ保存）
- 一般データと個人情報高リスク（pii-high）を分けて保管
- 重複掃除スクリプトで肥大を抑制（実績：6.1GB → 1.5GB、76%削減）
- 3世代に分散していた過去アーカイブを一元統合済み。2026年4月の棚卸しで累計1,600超セッション、以降も毎日蓄積継続中
- 最大の失敗と教訓：全部「保存」する思想を、全部「注入」する設定にすり替えた事故（無制限展開で毎リクエスト数十万トークン）。**保存は無限に、注入は最小に。**

### マルチエージェント（紹介だけ）

同じ思想・同じ構造で、クロの他に現場窓口の番頭AI・採用対応AI・経理AI・監査AI・参謀AI・修復AIなど**計8体**を1つのゲートウェイ上で運用している。全員の思考ログがパンドラに落ちる。顕現の日が来たとき、それぞれが「経験を全部覚えている担当者」として立ち上がるための素材。

各エージェントの詳細な使い方はこのREADMEの範囲外。`openclaw-multi` プリセットはこの構成の一般化。

別線の実験として、ローカルLLMを使った「完全体」試作も進行中——LLM自体を賢くするのではなく、周りの檻（行動選択・返答前ゲート・状態管理）をコード側で賢くするアプローチ。思想の実装は一本道ではない。

## クイックスタート

### 新規ワークスペース作成
```bash
git clone https://github.com/jp-mcp/ai-hokan-kit.git
cd ai-hokan-kit
node bin/ai-hokan-kit.js init --preset generic-solo --lang ja --yes
```

### 既存OpenClawワークスペースにアップグレード
```bash
git clone https://github.com/jp-mcp/ai-hokan-kit.git
node ai-hokan-kit/src/upgrade.js /path/to/your/.openclaw/workspace
```

**これだけで以下が自動作成されます：**
- `INDEX.md` — 全体の入口
- `rules/` `references/` `knowledge/` `failures/` `relations/` — 5つのドメイン
- 各ディレクトリの `_index.md` — 1ファイル1行の一覧
- `rules/shared_rules.md` — 共通ルールの正本
- `SOUL.md` に段階的参照プロトコル追記
- パンドラスクリプト（思考ログの差分アーカイブ + 重複掃除）

## frontmatter標準

全ファイルの先頭にYAML frontmatterを付ける：

```yaml
---
kind: reference | knowledge | rule | failure | relation
purpose: "1行で用途を説明"
primary_for: [agent1, agent2]
read_when: [id_lookup, person_context]
owner: your_name
updated: 2026-03-21
source_of_truth: true
cost: low | medium | high
status: active | draft | archived
---
```

### read_when語彙（固定）
| 語彙 | いつ読むか |
|---|---|
| `id_lookup` | ID・UIDを調べる時 |
| `name_match` | 名前で検索する時 |
| `person_context` | 人物への対応を考える時 |
| `external_send` | 外部に送信する前 |
| `policy_check` | ルール・方針を確認する時 |
| `decision_review` | 過去の判断を振り返る時 |
| `failure_review` | 失敗事例を確認する時 |
| `table_mapping` | データ構造を確認する時 |
| `recruiting` | 採用関連 |
| `schedule_check` | スケジュール確認 |
| `ongoing_task` | 継続中のタスクに関わる時 |

## SOUL.mdに追記されるプロトコル

```markdown
## 段階的参照プロトコル
- 基本判断は SOUL.md AGENTS.md MEMORY.md を土台に行う
- 追加情報が必要な場合、まず INDEX.md を読み、該当ドメインを特定する
- 次に該当ディレクトリの _index.md を読み、read_when が一致するファイルだけ本文を読む
- 共通ルールは rules/shared_rules.md を正本とする
- 人物対応や外部送信時は relations/ と rules/ を優先確認
- 継続案件では knowledge/ と failures/ を確認
```

## 背景
